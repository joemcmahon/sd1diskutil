## Learnings

**global[10:14] = pool.len(), not EVENT_LEAD_ZEROS + sum_ds:** The global declared-size field encodes the total pool section byte count. `EVENT_LEAD_ZEROS + sum_ds` is the "clean" version (no stale bytes), which underreports when stale pool bytes are present. The firmware uses this field to locate the event data boundary — wrong value = truncated or overrun reads. Verified against MAME `4.syx`: `global[10:14] == pool.len()`.

**Sliding window formula (from v1.14, still load-bearing):**
`hardware_header[slot] = disk_headers_flat[112 + slot*186 : 112 + (slot+1)*186]`
Byte 112 is a fixed Ensoniq disk format property. ThirtySeq must read from `disk` (≥6144 bytes) not `disk_headers` (5640 bytes) because window end for slot 29 is 5692 bytes.

**Stale ds clamping (from v1.14):** Native Ensoniq disks have all-0xFF undefined headers → ds reads as 0xFFFFFF = 16M bytes per slot → multi-GB output. Clamp to 0.

**Integration test skips gracefully:** `hw_sysex_headers_match_real_hardware_dump` returns early if `disk_with_everything.img` (in cwd) or `~/Downloads/4.syx` are absent. Runs locally, not in CI.

## Post-Mortem

### What Worked

- Fix was a single clean substitution at two identical sites — easy to verify correctness
- Existing integration test `hw_sysex_headers_match_real_hardware_dump` provided immediate confidence the change didn't break header output
- Pattern of "Sojus tests on hardware, reports bug with exact fix spec" working well — zero ambiguity about what to change

### What Failed

- Nothing failed this session; the fix was straightforward

### Key Decisions

- **Use `pool.len()` directly rather than recomputing:** pool is already built by the time global is written; using its actual length is simpler and guaranteed correct regardless of what stale bytes contributed
- **One commit for fix + release notes:** single-line bug fix, no reason to split
